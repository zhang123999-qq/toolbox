## 一、测试范围

被测对象是**二进制部署配套的全部命令行工具**，分三层：

| 层           | 入口                                            | 说明                                                      |
| ------------ | ----------------------------------------------- | --------------------------------------------------------- |
| 一键安装脚本 | `install.sh`（`curl … \| bash` 直链入口）       | 6 步流程：环境检查 → 解析版本 → 下载 → 校验 → 解包 → 落地 |
| 部署管理 CLI | `toolboxctl`（别名 `toolbox`，19 个子命令入口） | 安装 / 卸载 / 运维 / 在线升级                             |
| 发布源与制品 | 本地 `http.server` 源 + GitHub Release 直链     | 覆盖「下载 + sha256 校验」链路                            |

覆盖的子命令（19 个入口）：

`help` `-h` `--help` `version` `-v` `--version` `status` `config` `list` `doctor`
`health` `logs` `backup` `render` `install` `uninstall`/`remove`
`start` `stop` `restart` `reload` `check-update` `upgrade`/`update` `rollback`

主要使用场景：

1. **常规功能**：帮助/版本、只读信息（状态、配置、版本列表、自检、健康、日志）、
   备份、模板渲染、服务控制四件套。
2. **安装与重复安装**：全新安装、已装同版本的重复执行（一键脚本重跑）。
3. **在线升级**：查询可升级版本、同版本跳过、回退源跳过、真实升级、回滚。
4. **临时代理**：经代理从 GitHub 一键安装、经代理查询更新、
   代理环境变量下本地健康探测不被劫持、源不可达时明确报错。
5. **异常与边界**：非 root、越界端口、相对 `--prefix`、未知参数、非数字行数。

## 三、已修复问题

### 3.1 `upgrade` 对「回退源」会静默降级（严重）

- **现象**：源内版本低于当前版本时，`upgrade` 会真的把线上实例降级，而用户以为自己执行了一次升级。
- **触发场景**：镜像站过期、切回旧源、源内 `latest.txt` 未更新——都会让「源内版本 < 当前版本」。
- **根因**：原实现只处理 `target == cur`，没有处理 `target < cur`。
- **修复**：未显式指定 `--to` 时，只要**检测不到更高版本就跳过本次更新**，
  并给出 `rollback --to`（降级）与 `--force`（强制重装）两条可执行指引；
  显式 `--to` 仍视为明确意图，允许同版本重装或降级。
- **验证**：D-24 / D-24b / D-25。不仅断言输出含「跳过」，还要求服务未重启、
  且回退版本**没有**被落地成 release 目录。

### 3.2 `install` 对已存在版本直接报错，一键脚本无法重复执行（中）

- **现象**：`curl … | bash` 重跑（修坏掉的配置、重建实例都是常见操作）稳定失败，
  报「版本 0.0.1-beta 已存在」，且 `install.sh` 如实把它报成「安装失败」。
- **根因**：`cmd_install` 在版本目录已存在且未传 `--force` 时直接 `die`。
- **修复**：改为**幂等复用**已落地的 release，只重跑「切 current → 渲染配置 → 启服务」，
  与 `upgrade` 对已存在版本的既有行为对齐；`--force` 仍可强制覆盖重写。
- **验证**：D-30c。

### 3.3 `check-update` 打印的升级源类型恒为空括号（中）

- **现象**：`check-update` 输出「升级源 : https://…（　　　）」——括号里什么都没有，
  设计上应显示 `url` 或 `dir`。
- **根因**：`resolve_update_source` 是经 `$(…)` 命令替换调用的，而命令替换运行在
  **子 shell** 中，函数内对全局 `SOURCE_KIND` 的赋值传不回调用方。
- **修复**：函数改为返回「源类型 + 版本」一行，由调用方按第一个空格拆开，不再依赖副作用。
- **验证**：D-32b。

### 3.4 `logs -n` 不校验行数（低）

- **现象**：`logs -n abc` 把非法值原样丢给 `journalctl -n` 与 `tail -n`，
  两个命令各自报错、又被 `|| true` 吞掉，输出里混着报错却未必以非 0 退出。
- **修复**：要求正整数，非法值按用法错误退出（exit 2）。
- **验证**：D-12（期望退出码 2）。

### 3.5 制品层问题：Release 资产落后 + CDN 缓存（环境/流程，非代码）

- **现象**：D-30（经代理一键安装）稳定失败在「版本 0.0.1-beta 已存在」。
- **根因（两层）**：
  1. `install.sh` 下载 bundle 后执行的是**包内自带的 `toolboxctl`**；
     而 Release 资产仍是修复前的旧包 → 打到旧的「版本已存在即 die」逻辑。
  2. `gh release upload --clobber` 之后，`releases/latest/download/<name>`
     仍会在若干分钟内返回**旧内容**（CDN 缓存），期间下载到的还是旧包。
- **修复**：重新构建并 `--clobber` 刷新 Release 的 5 个资产；
  在 D 组代理段之前加 **Release 资产一致性预热闸门**（D-00c，最多等 90 s），
  并加 **D-30d** 用整包 sha256 比对，把资产漂移永久卡在测试里。
- **验证**：D-00c、D-30、D-30d。
