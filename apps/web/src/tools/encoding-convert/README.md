# 编码转换

文本与字节之间按指定字符集互相转换（UTF-8 / GBK / Big5 / Shift_JIS 等）。

> 规划表里的依赖是 `iconv-lite`，但本项目禁止新增 npm 依赖，
> 因此这里**只用浏览器原生的 `TextDecoder` / `TextEncoder`**（详见「实现要点」与「限制」）。

## 用途

- **乱码修复**：把被当作 Latin-1 读出来的乱码串，按原始字符集解码回来。
- **生成指定编码的字节**：给甲方系统（还在用 GBK 的老接口）准备中文报文字节。
- **核对字节**：看看一段字符串在某个字符集下到底会落成哪些字节（hex / base64）。

## 输入

| 字段   | 类型   | 约束              |
| ------ | ------ | ----------------- |
| `text` | string | 最大 500,000 字符 |

- `direction=encode`：输入是**文本**（工具内部按 UTF-8 承载）。
- `direction=decode`：输入是**字节**，写法由 `format` 决定。

## 输出

| 字段   | 类型   | 说明                     |
| ------ | ------ | ------------------------ |
| `text` | string | 转换结果；空输入返回空串 |

## 选项

| 选项        | 取值                                                                                                                    | 默认     | 说明                      |
| ----------- | ----------------------------------------------------------------------------------------------------------------------- | -------- | ------------------------- |
| `direction` | `encode` / `decode`                                                                                                     | `encode` | 文本 → 字节 / 字节 → 文本 |
| `encoding`  | `utf-8` `utf-16le` `utf-16be` `gbk` `gb18030` `big5` `shift_jis` `euc-jp` `euc-kr` `iso-8859-1` `windows-1252` `koi8-r` | `gbk`    | 另一端的字符集            |
| `format`    | `hex` / `base64` / `latin1`                                                                                             | `hex`    | 字节侧的写法              |

### 三种字节写法怎么选

| 写法     | 形态                | 适用场景                                 |
| -------- | ------------------- | ---------------------------------------- |
| `hex`    | `d6d0cec4`          | 报文、协议字段、字节数组                 |
| `base64` | `1tDOxA==`          | JSON / XML 里承载二进制                  |
| `latin1` | 一个字节 = 一个字符 | 直接贴网页上拷下来的「乱码串」来反向解码 |

## 实现要点

浏览器只提供**解码**器（`TextDecoder`），而 `TextEncoder` 固定只做 UTF-8，
单靠原生 API 无法把中文编成 GBK 字节。这里的做法是：枚举所有单字节与双字节序列，
用 `TextDecoder` 问出每个序列对应的字符，**反过来建立「字符 → 字节」表**
（`utils.ts` 的 `buildEncoderTable`）。不引入任何码表依赖，代价是首次使用该字符集时
一次性约 2.5 万次解码（十几毫秒），结果按字符集缓存。

`utf-8` 走原生 `TextEncoder`；`utf-16le` / `utf-16be` 按 UTF-16 码元直接写字节。

## 限制

- **覆盖范围受限于运行环境的 `TextDecoder`**：主流浏览器（含 full-ICU 的 Chromium / Firefox / Safari）
  与 Node 18+ 都提供表里的字符集；若某个环境没有，会明确提示
  「不支持的编码：xxx」并列出可选字符集。
- **只枚举一字节与两字节序列**，因此 GB18030 的四字节区（生僻字、部分扩展 B 之后的汉字）
  与 EUC-JP 的三字节区无法编码（解码不受影响，那是解码器的事）。
- 字符集里没有的字符**直接报错而不是静默替换**（不写 `?`、不做音译），
  报错里会列出最多 3 个不支持的字符。
- `latin1` 形式要求每个字符的码位 ≤ `U+00FF`；混进中文就报错提示改用 hex / base64。
- UTF-16 不加 BOM；`utf-16`（不带 le/be）这种依赖 BOM 判断字节序的写法不提供。
- 不做 IANA 名称别名归并（`EUC-KR` 与 `euc-kr` 都认得，但 `cp936`、`ms936` 之类不在列表里）。

## 数据流向

**纯本地处理。** 输入内容仅在浏览器内存中处理，不发送任何网络请求，不写入服务端。
`meta.api = false`，无需自备 API/Key。

## 示例

输入：`工具箱`，`direction=encode`、`encoding=gbk`、`format=hex`
输出：`b9a4bedfcfe4`

反向：`direction=decode`、`encoding=gbk`、`format=hex`，输入 `b9a4bedfcfe4`，输出 `工具箱`。
