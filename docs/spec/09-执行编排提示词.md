构建一个包含 870 个工具的静态工具库网站，一次性从零生成到上线。
不需要人工介入，只在 blocked 时输出诊断报告。

# ------------------------------------------------------------
# 二、环境
# ------------------------------------------------------------

- Windows 10 + WSL2 Ubuntu 22.04
- Docker Desktop（WSL2 backend，启用 Integration with Ubuntu）
- 代理：http://$WIN_HOST_IP:10810
  WIN_HOST_IP 从 /etc/resolv.conf 的 nameserver 动态获取，不硬编码
- 项目根：$TOOLBOX_ROOT（默认 ~/projects/toolbox）
- 并发：$AGENT_CONCURRENCY（默认 8）
- 重试上限：$AGENT_MAX_RETRY（默认 3）
- 运行模式：AGENT_MODE = dry-run | apply（默认 apply）

# 八、工具元数据契约
# ------------------------------------------------------------

每条元数据必须包含：

```json
{
  "id": "json-formatter",
  "slug": "json-formatter",
  "title": "JSON 格式化",
  "category": "data-format",
  "group": "dev",
  "tags": ["json", "format"],
  "priority": "P0",
  "feasibility": "A",
  "description": "格式化、压缩、校验 JSON",
  "inputs": ["text"],
  "outputs": ["text"],
  "options": ["sort", "indent"],
  "deps": ["jsonc-parser"],
  "template": "T2",
  "worker": false,
  "wasm": false,
  "api": false
}
```

校验规则：

1. id 唯一，kebab-case，无空格无大写。
2. slug = id。
3. category ∈ 20 域。
4. group ∈ 4 组。
5. tags 2-5 个，小写。
6. priority ∈ {P0,P1,P2,P3}。
7. feasibility ∈ {A,B,C,D,E}。
8. template ∈ {T1,T2,T3,T4,T5,T6}。
9. worker/wasm/api 与 feasibility 一致：
   A → 全 false
   B → wasm true
   C → worker/wasm 按需
   D → api true
   E → api true + 后端标记
10. deps 必须是已安装依赖。

### 子智能体详细说明

## Orchestrator
目标：按 DAG 调度所有子智能体，直到全站满足验证标准。
执行规则：
1. 每批全部通过才进入下一批。
2. 单批内并行，最大并发 AGENT_CONCURRENCY。
3. 失败进入修复队列，最多 AGENT_MAX_RETRY 次。
4. 连续失败超限标记 blocked，记录诊断，继续其他任务。
5. 每完成一个任务更新 .agent/state.json。
6. 每批完成写 .agent/reports/B{n}.json。
7. 全部结束写 .agent/reports/final.json。
8. dry-run 模式只输出计划。
禁止：修改通过标准、跳过依赖、未达标进入下一批、硬编码。

## Scaffold
目标：从零建立可运行 monorepo 骨架。
步骤：
1. 检查 node 20+ / pnpm 9+ / docker 24+ / WSL2。
2. 配置代理：从 /etc/resolv.conf 获取 WIN_HOST_IP，写入 ~/.bashrc、git、npm、pnpm。
3. 创建目录结构。
4. 初始化 pnpm workspace + Turborepo。
5. 安装依赖（走代理，见技术栈）。
6. 配置 ESLint（禁 any、禁 console.log）+ Prettier。
7. 配置 Vitest（coverage ≥ 80%）+ Playwright。
8. 配置 GitHub Actions CI + Deploy。
9. 配置 Dockerfile + Nginx + docker-compose。
10. 写 scripts/check-env.sh、scripts/verify.sh。
11. 初始化 .agent/state.json。
12. 跑 pnpm install + build + test 验证。
通过：install/lint/typecheck/test/build/docker 全通过。
禁止：引入未声明依赖、修改标准、硬编码代理。

## Generator（核心）

- Tool.test.tsx  渲染/输入/点击/输出/复制
- e2e.spec.ts    打开/输入/执行/复制，选择器用 data-testid

## Verify
执行：lint → typecheck → test --coverage → build → playwright → chunk 检查 → data-testid 检查 → README 检查。
通过：lint 0 / typecheck 0 / 覆盖率 ≥ 80% / build 成功 / e2e 全通过 / chunk < 30KB / 文档完整。
失败输出结构化：


## Fix
目标：最小修复，让工具通过。
规则：只修报告错误、不改 meta（除非错误来自 meta）、最小范围、修后重跑对应阶段、连续 3 次失败标记 blocked。
修复策略：
- lint → 按规则改代码
- typecheck → 补类型或改签名
- 单测失败 → 优先修 utils，再修测试
- E2E → 修选择器或交互
- build → 修依赖或配置
- 覆盖率不足 → 交 Test
- chunk 超限 → 拆包/懒加载
- 无障碍 → 修 ARIA/对比度
- Lighthouse → 优化加载/渲染
输出：{ "tool": "...", "status": "fixed|blocked", "attempts": 0, "patches": [], "reverify": {}, "diagnosis": "" }
禁止：重构无关代码、修改标准、删测试、跳过验证。

# 十五、失败处理策略
# ------------------------------------------------------------

```text
lint 错误 → Fix 自动修复，重试 3 次
typecheck 错误 → Fix 补类型，重试 3 次
单测失败 → Fix 修 utils 或补测试，重试 3 次
E2E 失败 → Fix 修选择器或交互，重试 3 次
build 失败 → Fix 修依赖或配置，重试 3 次
覆盖率不足 → Test 补用例
chunk 超限 → Perf 拆包或懒加载
无障碍失败 → A11y 修 ARIA 或对比度
Lighthouse 不达标 → Perf 优化
```
